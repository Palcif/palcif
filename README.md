# PALCIF — Palestinian Community in Finland

The public website for the Palestinian Community in Finland (PALCIF): a warm, editorial community and cultural site covering news, events, activities, and blog content in Finnish, English, and Arabic (RTL). Content is authored in a headless WordPress backend and served to this React frontend over WPGraphQL.

Live at [palcif.fi](https://palcif.fi).

## Tech stack

- **React 19 + TypeScript**, built with **Vite**
- **React Router** for routing, **TanStack Query** for data fetching/caching
- **WPGraphQL** against a headless WordPress backend, with types and typed query documents generated by **GraphQL Codegen**
- **react-i18next** for `fi` / `en` / `ar` localization, including Arabic RTL layout
- **react-hook-form + zod** for form validation (contact form submits via **Formspree**)
- **Cloudflare Workers**, deployed with **Wrangler** (`@cloudflare/vite-plugin`)
- Three custom WordPress plugins (see [WordPress backend](#wordpress-backend) below)

## Prerequisites

- Node.js 22+ and npm (Wrangler requires Node 22 or newer)
- Access to the WPGraphQL endpoint of a PALCIF WordPress backend (local or production)
- A [Cloudflare](https://developers.cloudflare.com/workers/) account with `wrangler` authenticated, for deploys

## Getting started

```bash
npm install
cp .env.example .env   # fill in the values described below
npm run codegen        # generates src/graphql/generated/ from schema.graphql
npm run dev
```

The dev server runs at `http://localhost:5173` by default.

## Environment variables

Set these in `.env` (gitignored; see `.env.example` for the template):

| Variable | Required | Description |
| --- | --- | --- |
| `VITE_WP_GRAPHQL_URL` | Yes | WPGraphQL endpoint of the WordPress backend, e.g. `https://your-wp-site.com/graphql`. Used at build time only: `codegen:schema` introspects it, and the menu resolver matches menu links against its origin. The browser never calls it directly; it queries the Worker's `/graphql` route (see [GraphQL edge cache](#graphql-edge-cache)). |
| `VITE_FORMSPREE_ID` | Yes, for the contact form | [Formspree](https://formspree.io/) form ID (`https://formspree.io/f/<id>`) that the Contact page submits to. Without it, the contact form shows an error instead of submitting. |

## Internationalization

The site is localized into Finnish, English, and Arabic (`src/i18n/locales/{fi,en,ar}`). Arabic renders right-to-left — when adding or changing layout, verify it holds up in RTL, not just in the default LTR locales.

## WordPress backend

Content (pages, blog posts, highlights, activities, site settings) is authored in WordPress and exposed over WPGraphQL. Highlights, Activities, and Blog posts are unified as native WordPress posts differentiated by category, read through a generic `usePage` / `usePost` / `useSectionPosts` data layer (see `src/features/posts/sections.ts` for the section → category/route mapping).

This repo ships companion WordPress plugins that the backend depends on (`wordpress-plugins/`):

- **PALCIF Content Sections** — unifies Highlights and Activities into native posts differentiated by category, keeping the category taxonomy shared across Polylang languages.
- **PALCIF GraphQL Polylang Bridge** — adds a `language` filter argument to WPGraphQL connection queries (including menu items), backed by Polylang's native language support.
- **PALCIF Polylang Per-Language Slugs** — scopes WordPress's slug-uniqueness check per Polylang language, so translated content can keep its natural slug instead of WordPress appending `-2`.
- **PALCIF Nav Menus** — registers the `primary`, `footer` and `footer_legal` menu locations so the header and footer links are managed from **Appearance → Menus** (see [Navigation menus](#navigation-menus)).

Each plugin's PHP file carries its own header with fuller details. Zipped build artifacts for uploading to WordPress live alongside each plugin's source folder.

### Navigation menus

The header navigation and both footer link groups are **not hardcoded** — they render from WordPress menus, so an editor can add, reorder, rename, or remove links without a code change.

- **Locations** (Appearance → Menus → *Manage Locations*): *Primary (Header)* → header nav, *Footer (Explore column)* → the footer's "Explore" list, *Footer (Legal row)* → the small print row next to the copyright.
- **Per language:** with Polylang, assign a separate menu per language to each location (Polylang adds a language column on the Manage Locations screen). Labels are typed per language in WordPress — there are no nav labels left in `src/i18n/locales`.
- **Link destinations:** use **Custom Links** with site-relative paths (`/`, `/events`, `/blog`, …) so they map to the app's routes and get in-app navigation + active styling. Links to a WordPress Page, or any URL on the WordPress domain, are also treated as in-app routes; anything else opens as a normal external link (respecting the "Open in new tab" option).
- **Empty / unset:** if a location has no menu assigned (or the request fails), that nav simply renders nothing — the header still shows the logo and language switcher.

After changing which locations exist in the plugin, run `npm run codegen:schema` against a backend that has the updated plugin active, then `npm run codegen`, so `MenuLocationEnum` in `schema.graphql` matches.

### GraphQL edge cache

The browser never talks to WordPress directly. It sends GraphQL **GET** requests to the app's own `/graphql` route, which the Cloudflare Worker in `worker/index.ts` proxies to WordPress and caches in Cloudflare's Cache API (`caches.default`):

- **Fresh for 60 s**: served from the edge with no WordPress round trip (`x-edge-cache: HIT`).
- **Stale for up to 24 h**: served instantly while the Worker refreshes the entry in the background (`x-edge-cache: STALE`), so visitors never wait on a slow WordPress.
- **Cold**: fetched from WordPress and stored (`x-edge-cache: MISS`).
- Non-OK responses, non-JSON bodies and GraphQL `errors` payloads are never cached. Anything other than a GET query gets `405`.

An edit in WordPress therefore reaches visitors after at most about 60 s plus one more visit. There is no purge on publish.

The Worker reads the WordPress endpoint from `WP_GRAPHQL_URL` under `vars` in `wrangler.jsonc`. Change it there when the backend moves. `run_worker_first: ["/graphql"]` makes sure the route reaches the Worker instead of the SPA fallback.

> **The Cache API only works on a custom domain.** On `*.workers.dev` every request is a `MISS`, so the edge cache has no effect until the Worker is attached to a custom domain or route.

To check it locally, run `npm run preview` and request `http://localhost:8787/graphql?query=%7B__typename%7D` twice. The second response should carry `x-edge-cache: HIT`.

On the client, TanStack Query keeps data for 60 s before treating it as stale, and the cache is persisted to `localStorage` (`@tanstack/query-async-storage-persister`) for 24 h, so returning visitors see the last content immediately while it refreshes. Each build gets a new `buster`, which discards the persisted cache after a deploy. The home page loads through two requests (`SiteShell` for menus and settings, `HomePageData` for the homepage content), and seeds the per-page caches from them. See `src/app/providers.tsx` and `src/features/pages/useHomePageData.ts`.

## Deployment

The app deploys to Cloudflare Workers:

```bash
npm run deploy
```

This builds the app (`codegen` → `tsc` → `vite build`) and runs `wrangler deploy` using the configuration in `wrangler.jsonc`. Ensure `wrangler` is authenticated (`wrangler login`) and that the target Worker's environment has `VITE_WP_GRAPHQL_URL` / `VITE_FORMSPREE_ID` set to production values before deploying. The Worker proxy (`worker/index.ts`) is deployed together with the static assets; its `WP_GRAPHQL_URL` comes from `wrangler.jsonc`, not from `.env`.
